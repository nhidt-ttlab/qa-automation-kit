## Project settings

This skill is part of the QA automation kit and works on any project that has a `qakit.config.yaml`.
Before starting:

1. Locate the project's `qakit.config.yaml` — the path named in the "QA automation kit" section of the
   project's `CLAUDE.md`, otherwise the repository root. Paths inside it are relative to its folder.
2. Read the settings this skill uses: `modules`, `paths`, `ids`, `locale`, `mcp` (tool names are
   `mcp__<serverName>__<tool>`), and `web` / `apiSources` where relevant.
3. Read the project knowledge for this skill, if present: `<paths.knowledge>/<skill-name>.md` and
   `<paths.knowledge>/project.md`. Knowledge files carry project facts — module scope, vocabulary,
   examples, known pitfalls — and win over this skill's generic examples. They do not relax this
   skill's process rules or quality gates.
4. Write documents in the project's `locale`. When a template exists for it, `templates/` holds the
   locale's version.

# Create Scenario Script

Use this skill for the **automation pass** — turning a finished test-step document into a runnable
`*.scenario.ts` inside the project's scenario harness (the TypeScript runner built on the kit's
`@qakit/core` and `@qakit/ui`; the knowledge file names its folder).

This skill writes **TypeScript**, not Markdown. Do not confuse it with `create-testcase-scenarios`,
which writes *scenario documents*. This one comes two passes later.

Notation used below:

- `<module>` — one entry of `modules` in the config.
- `<module dir>` — `module.stepDir ?? module.docSlug ?? module.id`.
- `<suite>` — `module.suite`. Several modules may share one suite folder.
- `<lane>` — `api` or `ui`.

| Pass | Skill | Output |
|---|---|---|
| Inventory | `create-testcase-inventory` | test-case inventory under `<paths.featureDocs>/<module.docSlug ?? module.id>/` |
| Scenario doc | `create-testcase-scenarios` | scenario documents under the same feature-doc folder |
| Steps (API) | `create-testcase-steps` | `<paths.steps>/api/<module dir>/<test-case id>-<slug>.md` |
| Steps (UI) | `create-testcase-steps-ui` | `<paths.steps>/ui/<module dir>/<test-case id>-<slug>.md` |
| **Automation (this skill)** | **this skill** | **`<paths.suites>/<suite>/<lane>/<slug>.scenario.ts`** |
| Run report | generated by the harness | `<paths.reports>`, `<paths.evidence>`, the run store (`reporting.sqlite`) — never hand-written |

The knowledge file states whether the project splits step docs by lane exactly as above.

## Required inputs

Read these before writing any code:

1. The harness's **authoring guide** for API and UI scenarios, if the project has one (the knowledge
   file names it and says which of its sections are stale). Where the guide's prose and the source tree
   disagree, **follow the tree**.
2. The **test-step doc** for this test case — the source of truth for the rule, the step matrix, and
   the assertion ids (matching `ids.assertion`, e.g. `A1`, `A2`, …). Never automate a rule the doc does
   not carry. Its sections follow `templates/api-test-steps.md` or `templates/ui-test-steps.md`; the ones
   this skill relies on are **Assertions**, **Pass / fail rule**, **Notes for automation**, **Open
   questions** and **Automation findings**.
3. The project's **reference implementations**, in the order the knowledge file lists them — typically
   one full-featured API scenario (mutation, several payloads, curated report), one read-only API probe
   with a standing blocker, and one UI scenario. Model the new file on the closest one.
4. The harness README — architecture rings, safety rules, evidence, run store.
5. The project's **mutation-constraints register**, when one exists — the per-test-case list of what may
   be automated as a hard assertion and what must stay `NOT_EVALUATED`.
6. The module's **API map** (typically `<paths.steps>/api/<module dir>/API-MAP.md`), when one exists.

## Architecture the file must respect

The harness is organised in four rings, dependencies pointing inward, and a fitness test enforces the
boundaries. The exact import aliases and folder names are in the knowledge file.

- **platform** — HTTP, browser, assertions, logger. Project-neutral; mostly thin re-exports of
  `@qakit/core` and `@qakit/ui`, bound to the project's widget adapters and locale.
- **app** — project-specific: data providers (resolving prerequisites against the target environment),
  flows (payload builders plus the HTTP calls), fixtures (non-live defaults and the test-data marker),
  screens and selectors.
- **suites** — `<paths.suites>/<suite>/<lane>/`, the test cases. **This is the only ring you add files to**
  (apart from new provider/flow functions in the app ring).
- **harness** — running and recording a run: registry, report pipeline, evidence, run store.

Rules that follow from it:

- **A scenario never imports the run store or `node:sqlite`.** Persisting a run belongs to the report
  pipeline, after the scenario function returns. State this in a boundary comment above the imports,
  the way the reference scenarios do — the fitness test enforces it.
- **New HTTP lookups go into the data provider or a flow module**, not inline in the scenario. Scenarios
  depend on the `DataProvider` interface, never on a raw endpoint.
- Import through the harness's subpath aliases, with the extension the project's module resolution
  requires (the knowledge file shows the exact form). Never reach into a ring with a relative path.

## Shape of an API scenario

```ts
// boundary comment (see above)
const TEST_CASE_ID = 'TC-ORD-A07';           // matches ids.testCase
const FEATURE_ID = 'ORD-LIST-02';            // optional — one of module.featureCodes: the SCREEN this case sits on
const TEST_CASE_NAME = '<name matching the step doc title, in the project locale>';
const TEST_OBJECTIVE = '<one sentence covering every rule this run validates>';

export interface <Slug>Options { /* fixture selector */; dryRun?: boolean; cleanup?: boolean; /* pin overrides */ }
export interface ScenarioTraceStep { title: string; ok: boolean; status?: number; data?: unknown }
export interface <Slug>Result { scenario: '<slug>'; dryRun: boolean; passed: boolean; blocked?: boolean;
  blockedReason?: string; checks?: CheckResult[]; steps: ScenarioTraceStep[]; error?: string;
  overview?: ReportOverview; detailTables?: DetailTable[]; reportModel?: QaReportModelOverride }

export async function run<Slug>Scenario(
  http: HttpClient, dataProvider: DataProvider, options: <Slug>Options, logger: Logger,
): Promise<<Slug>Result> { … }

function buildOverview(…): ReportOverview { … }
function buildReportModelOverride(…): QaReportModelOverride { … }
```

`CheckResult`, `check`, `HttpClient` and `Logger` come from `@qakit/core` (usually through the platform
ring's re-exports); the options/selector types, `DataProvider` and the report types come from the
project's own rings. The knowledge file has the exact import block and signature.

Above the `run…` function, a JSDoc block that a reader with the step doc but not the backend source
can follow: which test case this implements, where the doc's assumed contract diverges from the real
one, the exact backend class/method/DTO fields with file references (in the repository named by
`apiSources.<id>.repository`), any **wire gotcha** in bold with the date it was verified live, how the
scenario splits into parts, and a `TODO` carrying the project's unconfirmed marker for anything
deliberately uncovered.

Body order:

1. Resolve prerequisites via `dataProvider`; `steps.push({ title, ok, status, data })` for every
   meaningful call.
2. Precondition unmet → return `blocked: true` with a `blockedReason` that tells the operator exactly
   what to fix. Never fabricate data to force a pass.
3. Honor `options.dryRun` — build payloads, return early, no live mutation.
4. Boundary/negative checks first, then the positive path, via `check(label, expected, actual, testId)`.
   `testId` is `'<TEST_CASE_ID> / <assertion id>'`, matching the step doc's Assertions section and
   `ids.checkRef` — **exactly two segments, always** (e.g. `TC-ORD-A07 / A2`). Build every id through one
   helper and route screenshot evidence (`checkTestId`) through it too: that string is an exact join
   into the evidence manifest, so an id that drifts silently orphans its screenshots.

   When the assertion answers a row of a hardening checklist (`<paths.checklists>`), do **not** append
   the row to `testId`. Use the harness's checklist-trace helper: declare the trace, use its `ref('A1')`
   as the `testId`, and apply it to `checks` once before assembling the result — the row id, the sheet's
   exact expected-result text and its priority then travel in their own fields all the way to the
   reporting UI. Never retype the sheet's text into the scenario; the harness's checklist import reads
   it from the sheet. See Pass 5 of `checklist-to-ui-automation`; the knowledge file names the helper
   and the import command.
5. Match failures on a stable machine-readable error code (the flow module's error-code extractor),
   never on a localized message string.
6. Wrap live mutation in `try/catch` so a throw still reaches cleanup and still writes a report.
7. Cleanup always runs unless `options.cleanup === false`, defensively per entity. Prefer the product's
   own business teardown (cancel, close, archive) over a hard delete when the product has one — the
   knowledge file names the canonical teardown per entity.
8. Compute `passed` as the hard-failure signal, not the verdict — see below.
9. Build `overview` (required) and `reportModel` (optional but preferred) in helpers at the bottom.

## Shape of a UI scenario

Same skeleton, with these differences:

- Handler signature is `(ctx: UiScenarioContext)` — one argument, not four. `steps` are the recorded UI
  step records the driver returns (`ui.recordedSteps()`).
- **Check preconditions over the API before launching a browser.** Many front ends remove menu items
  and routes the user is not granted, so a missing permission looks identical to a broken page: probe
  the permission/configuration endpoint and the data volume first, and return `BLOCKED` — never `FAIL`.
  The browser accessor on the context is lazy for exactly this reason. The knowledge file names the
  permission endpoint and any probe script.
- **Assert on `pageErrors`, not `consoleErrors`,** unless the knowledge file says the deployed build
  keeps `console.*` calls. Production bundles often strip them, so `consoleErrors` reads 0 even when the
  app misbehaves. Use `checkNoPageErrors` from `@qakit/ui`'s UI checks.
- **Never infer dataset size from the DOM.** Data grids commonly paginate or virtualise client-side over
  one server page; take the row-count oracle from the API response.
- **Runs are read-only by default** — the `@qakit/ui` guard aborts every non-safe request to the
  application hosts (`web.allowedHosts`), and the harness does not clean up UI-created data. Writing
  needs the `safety.allowWritesEnv` switch set to `1` and must own its cleanup. POST endpoints that only
  read must be declared as lookups, or the guard aborts them too.
- Test-case ids use the project's **UI series** (e.g. `TC-ORD-U01`, per `ids.testCase` and the
  knowledge file) so they never collide with API numbering.
- Prefer the shared UI check helpers from `@qakit/ui` (`checkContiguousSequence`, `checkRequestObserved`,
  `checkAllContain`, `checkFormBlocksSave`, `checkNoEscapedWrites`, …) over hand-rolled comparisons.
- Locate elements through the driver and the widget adapters listed in `web.widgets`, not raw CSS
  selectors; the knowledge file lists the widget quirks of the application under test.

### Desktop (Electron) windows

When the step doc's screen is a window of the desktop app the config's `desktop` block describes, the same
UI scenario takes it from `ctx.desktop()` (WebdriverIO, `@qakit/desktop`) instead of, or as well as,
`ctx.ui()`. The kit's `docs/desktop-testing.md` has the driver's verbs.

- Pass the step doc's **Target** strings as they are (`id=…`, `role=button[name="…"]`, `a >> b`); the
  desktop driver reads the same grammar. Use `countMatching` / `readControlState` when "absent" is the
  expected answer — `readText` and `click` wait and then fail.
- Read main-process state with `app.executeMain((electron, ...args) => …)`, not through the window.
- **There is no read-only guard on a desktop run.** The app makes its own requests, so gate every
  data-changing step on `safety.allowWritesEnv` in the scenario and point the app at a test backend
  through `desktop.env`. Secrets typed into the app go through `DesktopDriver`'s `redact` list or are
  never passed as step titles.
- There is no browser network trace: assert server-side effects with `ctx.http` after the window step.
- `pageErrors` and the widget adapters are browser-lane only; a failed desktop step records its own
  screenshot, and the app's process logs are kept on a failed run.

## Verdict semantics — the part most often gotten wrong

`passed` is not the QA verdict. `deriveVerdict` in `@qakit/core` (surfaced through the harness's report
module) computes `PASS | PARTIAL | FAIL | BLOCKED | ERROR` from `checks` + `blocked` + the
`NOT_EVALUATED` marker.

- `passed = false` → a confirmed product defect or a hard execution failure, nothing else.
- `passed = true` stays true when the proven part succeeded, even with other checkpoints blocked.
- `blocked` / `blockedReason` → environment, fixture, permission, or unresolved-contract blockers.
  A flaky background job or approval-workflow hiccup is `blocked`, not `failed`.
- An assertion you looked at and could not decide gets the literal string `NOT_EVALUATED` in
  `expected` **and** `actual` — that is what turns an otherwise-clean run into `PARTIAL` instead of a
  misleading `PASS`. (The marker is matched at the start of the string, so `NOT_EVALUATED — <reason>`
  also works.)
- `reportModel.qaSummary.verdict` must agree with what `deriveVerdict` will produce. Never write
  `passed ? 'PASS' : 'FAIL'`.

## Registration — three edits, in this order

1. Add the scenario name to the harness's scenario-name registry (a per-suite enum for API scenarios, a
   UI enum for browser scenarios — the knowledge file names the files), with a doc comment naming the
   test-case id and the rule.
2. Import the handler and map it in the suite barrel `<paths.suites>/<suite>/<lane>/index.ts`. API
   barrels adapt the context to the four-argument signature; UI barrels pass the handler directly.
3. Do not add a per-scenario npm script. Scenarios run through the harness's generic single-scenario
   command, and the aggregate commands (all, per lane, per suite) select off a generated scenario-group
   index — regenerate it and the new scenario joins them on its own. A fitness test fails if the
   committed index drifts.

Adding a whole new `<suite>/<lane>/` folder also means registering the suite in the harness registry.

## Report wiring

The generated report is never hand-edited. If it renders badly, fix the scenario or the harness's
report translation tables (the knowledge file names them):

- new step-title shape → add a step-title rule
- new check label → add a check-label rule so it reads as a business sentence in the project locale
- brand-new endpoint → add an API-call-purpose rule

`overview.keyData` carries every identifier a reviewer needs to find the run's data (names, not bare
ids, plus every record number created). `overview.highlights` derives each bullet from a specific
check and states what was confirmed or what broke. `overview.attention` names the single worst thing —
confirmed bug > unverified blocker > first failing check — and is left unset only when the run is clean.

## Traceability contract — the test-case id must appear inside the file

The scenario file is TypeScript, so it carries no frontmatter. The `TestCase → Automation` edge is
recovered by scanning file **content** for ids matching `ids.testCase`. In practice nearly every
scenario file carries its id, which is why this edge needs no metadata layer (the knowledge file has
the measured figure).

- Write the test-case id verbatim in the file — the title/description string is the natural place.
- One exception is legitimate: an infrastructure or fixture spike that belongs to no test case.
  Mark it clearly (a `SPIKE-*` id, when `ids.testCase` allows one) so it reads as deliberate rather
  than as a missing id.
- **Never join a scenario to a module by its suite directory.** Suites are organised by API domain and
  are many-to-many with doc modules (`modules[].suite` shows several modules sharing one suite). The
  test-case id is the only reliable key.

## Hard rules

- **Do not invent** endpoints, actionIds, field names, formulas, enum values, or error codes. If it is
  not in the step doc, the API map, or traced backend source (`apiSources.<id>.repository`), it stays
  marked unconfirmed (the project's marker, see the knowledge file) and its assertion stays
  `NOT_EVALUATED`.
- **One rule per scenario file.** Multiple test cases may share flows and fixtures, but each distinct
  rule gets its own file, named for the concept (`<slug>.scenario.ts`, kebab-case), not the test-case id.
- **Every assertion id from the step doc's Assertions section appears** as a `check(...)` `testId`, or
  explicitly as `NOT_EVALUATED` with the reason in `blockedReason`/`highlights`. Silently dropping one
  is a defect.
- **Reuse before writing.** Check the app ring's flows and providers for an existing call; a duplicate
  payload builder is how the two halves drift apart.
- API scenarios create real data in a shared environment — the test-data marker (`safety.testDataMarker`,
  applied by the module's fixture helper) is mandatory so test data is never confused with business data.
- The project `locale` for everything a human reads (check labels, overview, `blockedReason`, report
  model); original casing for identifiers, endpoint paths, field names, and error codes so they stay
  greppable.

## Workflow

1. Read the step doc end to end; list its assertion ids, its unconfirmed items, and its pass/fail rule.
2. Resolve every unconfirmed actionId against the API map, the API MCP server
   (`mcp__<mcp.apiServerName>__load_domain_api_registry` / `plan_task`), and — decisive — the backend
   source in `apiSources.<id>.repository`. The OpenAPI spec proves an endpoint exists, not the field
   mapping. When you need the payload *shape* — enum values, date format, which fields the screen really
   sends — trace it from live traffic: [`references/api-contract-tracing.md`](references/api-contract-tracing.md).
3. Decide, per assertion, whether it is automatable now or must ship `NOT_EVALUATED`; cross-check the
   mutation-constraints register before promoting anything to a hard assertion.
4. Write the scenario, then register it.
5. The harness typecheck and unit tests (fitness + report tests) must both pass.
6. Run the scenario in dry-run mode to sanity-check data resolution and the payload.
7. Run live. Read the generated report; add any missing translation-table entries.
8. Append an **Automation findings** section to the step doc (the last numbered section of the
   template) — what source-tracing corrected, with class/method/DTO references. It *corrects* the
   earlier sections rather than editing them, keeping the honest record of "what we assumed" vs.
   "what we verified".
9. Write a manual recap report (location and naming in the knowledge file) only when the run is
   `PARTIAL`/`BLOCKED`/`FAIL` or found a bug.

The knowledge file maps each step to the project's exact commands.

## Verification before declaring done

- Typecheck clean; unit tests clean (the architecture fitness test is the boundary guard).
- The harness's scenario listing shows the new name — if it does not, the registry enum or the barrel is
  missing an entry.
- The generated scenario-group index was regenerated and its drift test passes.
- Every assertion id from the step doc is accounted for; the `NOT_EVALUATED` count matches what the step
  doc's blockers justify.
- The run's derived verdict matches `reportModel.qaSummary.verdict`.
- No endpoint in the file is absent from the API map.
- Nothing under `<paths.reports>`, `<paths.evidence>`, the harness's raw-output folder or the run store
  was hand-edited.

## Avoid

- Coding straight from a scenario doc with no step doc — the assertion ids come from the step doc and
  are load-bearing downstream.
- Forcing a green run: fabricated fixture data, an assertion loosened to match observed behavior, or a
  blocker reported as `passed`.
- Collapsing a partially-verified run into `PASS` instead of `PARTIAL`.
- Asserting on a localized error message instead of the error code.
- Hand-editing a generated report to make it read better.
- Skipping cleanup, or hard-deleting when the product has a business teardown.
- Calling an endpoint directly from the scenario when the lookup belongs in the data provider.
